# Grouped material entry

Material Master’s Add material dialog, Buyer Create RFQ’s Materials step, and the supplier price book’s Add materials by category action share a responsive group editor. Choose an existing main category and subcategory once. Each row holds its description and unit. Only RFQ rows have quantity; supplier rows have a private SAR price and require selecting an existing master material. Existing single-record editing and custom supplier offers remain available.

Save Group retains the category pair. Save and Next Subcategory retains the main category and clears the subcategory. Add Another Main Category saves before clearing both selectors. Categories are locked while descriptions are present to prevent accidentally moving unsaved rows. Rows can be edited, removed, or pasted as tab-separated description/unit/quantity values (quantity only for RFQs). Supplier rows are selected through debounced, paginated master search. Drafts use session storage scoped to the authenticated user, workspace, and organization. New RFQ form data and added groups survive refresh; binary attachments must be selected again after refresh.

## API

- `POST /api/v1/taxonomy/materials/group`: admin only. Body: existing `main_category_id`, optional `subcategory_id`, optional `discipline` (Civil/Mechanical/Electrical), and 1–30 `rows` of `{description, unit}`. Returns `{materials, created, reused}`. Validates hierarchy and active units, locks the selected leaf category, fetches candidate descriptions together using existing indexes, and commits once. Exact normalized description/unit matches retain their IDs; ambiguous or archived records require review. Different diameters/grades in descriptions retain distinct identities. No category, quantity, or supplier-rate records are created by this endpoint. The UI submits larger groups in chunks of 30; on interruption it retains the draft, and resubmitting safely reuses completed chunks.
- `POST /api/v1/pricebooks/group`: organization-authorized supplier/admin writes. Body: `org_id`, existing `main_category_id`, optional `subcategory_id`, and 1–30 existing `PriceIn` rows. Each row must reference an active master in that group and the same organization. Existing price-book validation, capability handling, history, and permissions apply. A matching active material/basis/price/unit is reused on retry. A conflicting rate must be edited separately. Each chunk commits atomically. Currency remains SAR, as in the existing price book.
- `POST /api/v1/imports/materials/preview`: accepts existing XLSX/CSV staging plus `approved_only=true`. The updated admin UI always sends this flag. Standalone group headings and carried-forward category cells are supported; heading rows never become materials. Preview returns `detected_groups`, including source labels, material counts, and resolved category IDs. Unknown groups remain conflicts.
- `POST /api/v1/imports/materials/{batch_id}/preview-options`: accepts `group_mapping`, a JSON object keyed by the preview group key, with `{main_category_id, subcategory_id}` values. Only the uploading admin can reparse the preview. Targets must be existing active categories with a valid parent/child relationship. Confirmation and failed-job retry retain their existing routes and durable batches of 30. Imported quantity columns are ignored by Material Master. Different technical specifications are flagged for review instead of silently merged. Legacy flat import API behavior is retained; detected heading groups still require approved category mapping.

No database migration is required. Existing taxonomy, material identities, RFQ snapshots, matching, and supplier relationships are retained. RFQ quantities must remain greater than zero under the existing API contract; zero rows produce an actionable validation error and can be removed.

- Frontend typecheck and production build passed (`NEXT_BUILD_DIR=.next-grouped-entry`; the default build directory was locked).
- `node tests/grouped-material-browser.mjs` passed against the final build: ten materials, row edits/removal, duplicate validation, group transitions, failed-save recovery, mobile 320/375, Arabic RTL, RFQ zero-quantity rejection, RFQ draft recovery after refresh, and supplier master linkage. It uses HTTP fixtures without real accounts or database writes. Screenshots are stored under `frontend/.test-runtime/grouped-entry/`.
- Existing frontend API suite: 65 passed, 13 failed in untouched directory/profile/sitemap tests (module-resolution/mock issues and the HTTP sitemap check). Existing RFQ material-row tests passed.
- An initial unrestricted backend run had 262 passes and one failure from a blocked live PostgreSQL smoke-test connection. Subsequent verification used isolated SQLite. Live PostgreSQL concurrency and external services were not exercised.
